1. Tipos de requisitos

Requisito = descrição do que o sistema deve fazer (serviços) e das restrições sob as quais deve operar.

a divisão principal

Funcionais × Não funcionais

Funcional (RF): o que o sistema faz — serviços, reações a entradas, comportamento em situações específicas.

RF01 – O sistema deve permitir que o cliente emita a 2ª via do boleto.

Não funcional (RNF): como o sistema deve ser / restrições de qualidade: desempenho, segurança, usabilidade, confiabilidade, portabilidade…

RNF01 – 95% das consultas devem responder em até 2 segundos.
Truque: se der para escrever como "o usuário pode fazer X", é RF. Se fala de quão rápido / seguro / fácil / disponível, é RNF.
sommerville

Classificação dos RNF

TipoExemplos
De produtoDesempenho, eficiência, usabilidade, confiabilidade, segurança, portabilidade, espaço
OrganizacionaisProcesso e padrões da empresa: linguagem obrigatória, metodologia, prazo de entrega, ambiente operacional
ExternosLegais (LGPD), éticos, regulatórios, interoperabilidade com sistemas de terceiros
níveis

Requisitos de usuário × de sistema

De usuário: linguagem natural + diagramas, alto nível, para clientes e gestores.

De sistema: descrição detalhada e precisa (funções, serviços, restrições), base do contrato e do projeto; para desenvolvedores.

Usuário: "O sistema deve gerar relatório mensal de vendas."
Sistema: "No último dia útil do mês, às 23h, o sistema deve gerar PDF com total por vendedor, filtrado por loja, e enviá-lo ao e-mail do gerente."
outros tipos

Domínio, regras de negócio e restrições

  • Requisitos de domínio: vêm do domínio da aplicação (leis, cálculos, terminologia da área). Ex.: "o cálculo do INSS segue a tabela progressiva vigente".
  • Regras de negócio: políticas da organização. Ex.: "aluno com 3 livros emprestados não pode pegar outro".
  • Restrições (de projeto/implementação): limitam a solução. Ex.: "deve usar PostgreSQL".
  • Requisitos inversos: o que o sistema não deve fazer. Ex.: "não deve armazenar o CVV do cartão".
qualidade

Características de um bom requisito

  • Correto e necessário
  • Não ambíguo — uma única interpretação
  • Verificável / testável — dá para medir
  • Completo, consistente (não contradiz outro)
  • Rastreável — origem e impacto conhecidos (ID único)
  • Priorizado e viável
"O sistema deve ser fácil de usar" ✗ (não verificável) → "Um usuário novo deve concluir uma compra em até 3 minutos sem ajuda, em 90% dos testes" ✓
modelos

FURPS+ e ISO/IEC 25010

FURPS+: Funcionalidade, Usabilidade, Reliability (confiabilidade), Performance (desempenho), Suportabilidade (manutenção) + restrições (projeto, implementação, interface, físicas).

ISO 25010: adequação funcional, eficiência de desempenho, compatibilidade, usabilidade, confiabilidade, segurança, manutenibilidade, portabilidade.

Processo: elicitação (entrevistas, questionários, observação, workshops, prototipação) → análise/negociação → especificação → validação → gerenciamento (mudanças e rastreabilidade).

2. Modelagem de casos de uso

Mostra quem usa o sistema (atores) e para quê (casos de uso) — a visão externa, sem detalhes de implementação.

elementos

Ator, caso de uso, fronteira

  • Ator (boneco): papel externo que interage com o sistema — pessoa, outro sistema, hardware ou o tempo (tarefas agendadas). Não é um usuário específico.
  • Caso de uso (elipse): funcionalidade que entrega resultado de valor ao ator. Nome = verbo no infinitivo + complemento ("Emprestar livro").
  • Fronteira do sistema (retângulo): casos de uso dentro, atores fora.
  • Associação (linha contínua): ator participa do caso de uso.
o que mais cai

«include» × «extend»

«include»«extend»
QuandoSempre executa (obrigatório)Às vezes (condicional/opcional)
Setatracejada, do base → incluídotracejada, da extensão → base
UsoReaproveitar comportamento comumComportamento extra em um ponto de extensão
ExemploSacar dinheiro → Validar senhaCalcular multa → Devolver livro
herança

Generalização

Linha contínua com triângulo vazio apontando para o mais geral.

  • Entre atores: Gerente → Vendedor: o Gerente faz tudo que o Vendedor faz e mais.
  • Entre casos de uso: "Pagar com Pix" e "Pagar com cartão" especializam "Realizar pagamento".
especificação textual

Descrição do caso de uso

  • Nome, ID, atores (principal e secundários)
  • Pré-condições: o que deve ser verdade antes (ex.: aluno autenticado)
  • Fluxo principal (básico): o "caminho feliz", passo a passo ator ↔ sistema
  • Fluxos alternativos: variações válidas que ainda alcançam o objetivo
  • Fluxos de exceção: erros que impedem o objetivo (cartão recusado)
  • Pós-condições: estado após o sucesso (empréstimo registrado)
  • Regras de negócio relacionadas
pegadinhas

Erros comuns

  • Caso de uso como passo/tela ("Clicar em salvar", "Tela de login") ✗
  • Usar setas de associação para indicar ordem/fluxo ✗ (caso de uso não mostra sequência)
  • Colocar o banco de dados como ator ✗ (é parte do sistema)
  • Inverter a direção de «extend» ✗
  • Abusar de «include» para decompor funcionalmente tudo ✗

avançado

Classe associativa, interface, dependência

  • Classe associativa: dados da própria relação N:N. Aluno * — * Disciplina, ligada por tracejado a Matrícula (nota, frequência).
  • Interface/realização: tracejado + triângulo vazio: CartaoCredito ⇢▷ «interface» Pagavel.
  • Dependência: tracejado com seta aberta: uma classe usa outra temporariamente (parâmetro, variável local).
  • Navegabilidade: seta na associação: A conhece B, mas não necessariamente o contrário.

4. Modelagem de estados

Diagrama de máquina de estados: o ciclo de vida de um objeto — em que situações ele pode estar e quais eventos o fazem mudar.

notação

Elementos

  • Estado inicial: círculo preenchido (pseudoestado, só uma saída)
  • Estado final: círculo com anel
  • Estado: retângulo arredondado
  • Transição: seta com evento [guarda] / ação
  • Escolha: losango com saídas guardadas
o rótulo da seta

evento [guarda] / ação

  • Evento: o gatilho (pagar, after(30min) = tempo, when(saldo<0) = mudança).
  • Guarda [entre colchetes]: condição avaliada quando o evento ocorre; se falsa, a transição não dispara.
  • Ação (após a barra): executada durante a transição, rápida e não interrompível.
Aberto —— pagar [valor ≥ total] / emitirRecibo() ——▶ Pago

Evento que não tem transição no estado atual é ignorado.

dentro do estado

entry / do / exit

  • entry / ao entrar no estado
  • do / atividade contínua enquanto está no estado (pode ser interrompida)
  • exit / ao sair

Autotransição (seta saindo e voltando ao mesmo estado) executa exit e entry de novo; a transição interna (evento / ação escrita dentro do estado) não sai do estado.

avançado

Compostos, histórico e concorrência

  • Estado composto: contém subestados (ex.: "Em uso" com "Tocando" e "Pausado").
  • Histórico (H): ao voltar ao estado composto, retoma o último subestado ativo, em vez do inicial. H* = histórico profundo.
  • Regiões ortogonais (linha tracejada dentro do estado): subestados concorrentes.
  • Estados × atividades: diagrama de estados = ciclo de vida de um objeto; diagrama de atividades = fluxo de trabalho.
